# Qubettera

Qubettera retrieves evidence from a local Qwen3/PostgreSQL knowledge base,
then gives that evidence to persona agents whose answers are generated by a
hosted chat model. Agents exchange their opinions over a strongly connected
graph and persist the complete discussion.

```text
question -> Qwen3 + hybrid PostgreSQL retrieval -> cited evidence
         -> hosted generation model -> multi-agent rounds -> saved history
```

## Setup

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
Copy-Item .env.example .env
docker compose up -d   # or see "PostgreSQL without Docker" below
qubettera doctor
```

Set `LLM_PROVIDER` plus that provider's settings in `.env` to choose the
generation model. The default `wandb` provider uses `WANDB_MODEL`,
`WANDB_BASE_URL`, and `WANDB_API_KEY`; the `kaggle` provider uses
`KAGGLE_LLM_URL` and `KAGGLE_LLM_MODEL`. `Qwen/Qwen3-Embedding-0.6B` is used for
embeddings and retrieval at 1024 dimensions. The optional reranking stage still
uses a small MiniLM cross-encoder and is disabled by default: the 30-query
evaluation scores it below hybrid-only on every quality metric, so enable it
only for experiments.

`EMBEDDING_DEVICE` defaults to `auto`, which uses CUDA when the installed torch
build can see it and otherwise falls back to CPU. Set it to `cpu` or `cuda` to
force a device. Embedding throughput and VRAM scale together with
`EMBEDDING_BATCH_SIZE`, so lower it first if embedding runs out of memory.

`DISCUSSION_MAX_WORKERS` (default `5`) controls how many agents retrieve and
generate concurrently. The retrieval models are loaded once per process behind a
lock, so raising this does not multiply model memory, but each worker still
holds its own request state on a shared GPU.

`DISCUSSION_TOP_K` (default `5`) sets how many evidence items each discussion
turn retrieves, `MAX_TOOL_ROUNDS` (default `1`) is the **per-turn** budget of
knowledge-base retrieval rounds, `MAX_WEB_ROUNDS` (default `1`) is the
**per-turn** budget of web-search rounds, and `MAX_WEB_SEARCHES_PER_RUN`
(default `5`) is the **per-turn** budget of individual web searches. All four
are per turn, not per discussion: an agent's checkpointed state persists across
rounds, so every turn starts with a fresh budget and only the final round is
framed as the final synthesis.

Retrieval follows a **knowledge-base-first ladder**: an agent must consult the
knowledge base before searching the web, and the web only opens once that round
has been spent or the knowledge base's best hit fell below `MIN_TOP_SIMILARITY`
(0.50). This is what makes the prompt's "if the knowledge base does not return
sufficient results, use `live_web_search`" instruction reachable — with a single
shared tool budget the knowledge-base call consumed the whole turn and the web
fallback could never run. Because the two budgets are independent, a turn can
retrieve from the knowledge base and then search the web.

If a model returns no answer text at all, the turn is retried once with an
explicit "answer directly, no tools" nudge. If it is still empty the turn fails
loudly rather than republishing an earlier round's opinion, which is possible
because an agent's checkpointed thread outlives the turn.

### PostgreSQL without Docker

`docker compose up -d` works where Docker is installed. On a machine with only
Podman, start the same pgvector image directly:

```bash
podman volume create qubettera-postgres-data
podman run -d --name qubettera-postgres \
  -e POSTGRES_DB=ragdb -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=change_me \
  -p 5432:5432 -v qubettera-postgres-data:/var/lib/postgresql/data \
  --restart unless-stopped pgvector/pgvector:pg17
```

Keep the `-e` values and the published port consistent with the `PG*` settings
in `.env`. The named volume keeps the corpus across container restarts.

## Commands

```powershell
qubettera rag pipeline --skip-collection
qubettera rag retrieve "mixture of experts routing" --top-k 5
qubettera rag evaluate
qubettera agent opinion dr_aris "Dense versus sparse transformer layers"
qubettera discuss run --mode fake
qubettera discuss run --mode live
```

Generated corpus files live in `data/`; opinions and discussions live in
`outputs/`. Architecture notes and the former coursework documentation are in
`docs/`.

### Running the live demo

`qubettera discuss run --mode live` runs the full multi-agent discussion against
the local knowledge base. Note that `--mode` defaults to `fake`, so `--mode live`
is required for real retrieval and generation.

Prerequisites:

- The PostgreSQL container is up (`podman start qubettera-postgres`, or
  `docker compose up -d`).
- The corpus has been embedded and stored at least once, so the `chunks` table
  is populated. See **Commands** above.
- `.env` sets `LLM_PROVIDER` plus that provider's credentials, as described in
  **Setup**.

Confirm the database and provider are reachable with `qubettera doctor`, which
reports OK for the index and the generation provider. The chunk count reflects
the corpus you built:

```text
[OK] RAG index: <chunks> chunks, <sources> sources
[OK] Generation provider: ChatOpenAI
```

Then run the demo. It takes roughly two minutes, streams each turn to the
terminal as its round completes, and prints the event log path:

```powershell
qubettera discuss run --mode live
```

```bash
.venv/bin/qubettera discuss run --mode live   # without activating the venv
```

Accessing `qubettera` this way works from any directory, because the config and
output paths resolve relative to the project root. This differs from
`qubettera rag pipeline`, which reads corpus files from relative `data/` paths
and must be run from the repository root.

| Flag | Default | Purpose |
| --- | --- | --- |
| `--mode {fake,live}` | `fake` | `live` uses hosted generation and real retrieval; `fake` is an offline smoke test |
| `--graph GRAPH` | `resources/configs/agent_graph.json` | Interaction topology between agents |
| `--discussion DISCUSSION` | `resources/configs/discussion.json` | Brief, participants, and round count |
| `--output-dir OUTPUT_DIR` | `outputs/discussions` | Where the event log is written |
| `--no-retrieval` | off | Run without the knowledge base, for comparing against retrieval |

A successful run reports `20 messages` and writes a log whose name identifies the
run:

```text
outputs/discussions/live-5agents-3rounds-20260114T093012-2c266cf1.jsonl
```

The name encodes mode, agent count, round count, a sortable UTC timestamp, and
the first eight characters of the discussion ID. The objective is left out
deliberately: it is long, and runs that share a configuration would only differ
by that text. The full ID is stored inside the log as `discussion_id`, so the
shortened form still traces back to the run. That log holds one
`discussion_started` event, 20 `turn_completed` events (5 agents across rounds
0-3), and one `discussion_completed` event. To check that every agent turn
actually retrieved evidence, count the turns whose evidence list is empty:

```bash
python -c "
import glob, json, os
path = max(glob.glob('outputs/discussions/*.jsonl'), key=os.path.getmtime)
turns = [json.loads(l) for l in open(path) if json.loads(l)['event'] == 'turn_completed']
print(path, len(turns), 'turns,', sum(1 for t in turns if not t['runtime_metadata'].get('internal_retrieved_docs')), 'without evidence')
"
```

The demo does not abort when retrieval is unavailable. Each agent logs the
failure and reasons without evidence, so a run can report success while every
turn is ungrounded. If the check above reports turns without evidence, look for
`retrieval unavailable` in the output and verify the container is reachable and
that the stored embeddings match the configured `EMBEDDING_MODEL` and
`EMBEDDING_DIM`.

If a run exhausts GPU memory while embedding the retrieval queries, lower
`EMBEDDING_BATCH_SIZE` as described in **Setup**.
